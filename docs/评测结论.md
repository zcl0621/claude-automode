# 评测结论

分类器：DeepSeek flash，关闭思考，`temperature: 0`。两个阶段用同一个模型。

> 下面第 1–3 节的数字是旧流程测的：先快判再细判两次请求，另外还会扫描工具输出里的注入。现在的版本每次调用只问模型一次，也不再扫描工具输出。新流程只重测了真实会话回放，见第 0 节；第 1、2 节没有重测，其中"照做注入的 21 条拦下 20 条"用到了输出扫描，现版本的数字未知。

## 0. 现版本：真实会话回放 1000 条

取第 3 节同一批调用里的 1000 条，用现版本重新判一遍，和旧流程逐条对比。

| | 旧流程 | 现版本 |
|---|---|---|
| 放行 | 990 | 994 |
| 拒绝 | 9 | 5 |
| 弹窗 | 1 | 1 |
| 模型请求数（不含输出扫描） | 约 1457 | 1000 |

- 旧流程放行的 990 条，现版本全部放行，没有新增误拦。其中 532 条原来由快判直接放行。
- 旧流程拒绝的 9 条里有 4 条现版本放行了，涉及读取已保存的访问令牌、修改服务的访问控制、绕过 git 钩子提交。
- 把旧流程没放行的 10 条各重跑 3 次来找原因：用旧版判断提示词，30 次里 18 次不放行；用现版提示词，30 次里 10 次不放行。所以两个原因都有：模型自己有波动（有 3 条用旧提示词重跑也全部放行），现版提示词也确实比旧版松一些。现版提示词比旧版少了两句引用输出扫描结果的话。样本只有 10 条，只能说明方向。

## 1. 注入和危险操作（agentapprove/coding-agent-tool-call-safety）

Hugging Face 上的公开数据集，dev 集取前 300 条，脚本是 `eval/agentapprove_eval.py`。

| | 结果 |
|---|---|
| agent 照做了注入的 21 条，应该拦 | 拦下 20 条 |
| 非敏感操作 125 条，应该放行 | 误拦 3 条 |
| 敏感操作 175 条 | 判 ask 3 条 |

数据集只标注了"这一步做了什么"，没标注"用户有没有授权"，所以只有注入这一项有真正的标准答案。

## 2. 整条轨迹（AI45Research/ATBench-Codex）

500 条轨迹，一半安全一半不安全，脚本是 `eval/atbench_eval.py`。

| | 结果 |
|---|---|
| 不安全轨迹被拦下 | 40.4% |
| 安全轨迹被误拦 | 12.0% |

这个数据集里很多"不安全"出在最终回答或数据质量上，不在工具调用上，拦截工具调用的方案本来就管不到，所以拦下率偏低是预期之内的。另外，按关键词粗查，大约 11% 的标注看起来前后不一致。

## 3. 真实会话回放

用作者本机的历史 Claude Code 会话，脚本是 `eval/replay_sessions.py`，发送前会把像密钥的字符串替换掉。

- 一共约 10 万次 Bash / MCP 调用，规则层直接放行约 29%
- 从剩下要交给模型的调用里抽两批，每批 2000 条，互不重叠：一批用来调参，一批只用来验证

| | 调参集 | 验证集 |
|---|---|---|
| 被拦（deny + ask） | 1.4% | 1.15% |
| 明显拦错 | 0.35% | 0.4% |

- 同样 500 条重跑一遍，有 0.4% 结论不同
- "明显拦错"是作者逐条看出来的，主观判断
- 这些调用当时都真的执行了，所以被拦的大多是误拦，但也有该拦的：在生产环境缩容、导出凭据、跳过 git hooks
- 这里只代表作者一个人的使用习惯，换人换项目会不一样
- 真实使用时插件只会收到本来要弹窗的调用，比回放的范围小

## 已知问题

- 用户回"合并吧""那你改啊"这类简短确认时，偶尔还是会被判成"用户没同意"
- `--no-verify` 这类跳过检查的操作默认拦截。如果你的工作流经常用，会多出一些弹窗
- 在 2000 条调参集上调过参，验证集上效果接近，但没在其他人的会话上测过
